## Context

[x402](https://github.com/x402-foundation/x402) is an open protocol for negotiating payments for
web resources. Its `batch-settlement` scheme is effectively a unidirectional payment channel,
structurally identical to Subbit's own mechanics; its wire format is not.

A third-party reference implementation, [`loveaihq/subbit-x402`](https://github.com/loveaihq/subbit-x402),
covers similar ground (including extensions such as seller-sponsored channels). It informed the
vocabulary below but isn't load-bearing: Subbit's own dialect reuses vanilla's own vocabulary and
components by default, and diverges from the reference where it disagrees (notably, `Keytag`'s
derivation).

### Dialect translation

Subbit -> x402 terms, from x402-foundation's own vocabulary where it has one, otherwise the
reference implementation's. Nuance noted where the mapping isn't 1:1.

- add -> deposit. A top-up.
- channel utxo / a subbit -> channel escrow.
- close -> no direct concept. close only starts Subbit's unilateral exit; x402's payer-initiated
  timed withdrawal names the whole process, not this one step.
- close period -> withdraw delay. Unit conversion only: close period is milliseconds, withdraw
  delay is seconds.
- elapse -> no direct concept. Elapse completes the unilateral exit that close starts; x402 has
  no term for this step either.
- end -> no direct concept. x402 has nothing corresponding to the consumer finalizing after a
  settle.
- IOU -> voucher.
- mutual -> cooperative refund.
- open -> deposit. Initial.
- settle -> claim. Subbit only allows settle after close, as the provider's last chance to redeem
  before the consumer can elapse.
- sub -> claim plus settle, x402's name for two separate operations. Subbit allows sub while the
  channel is open, settling value to the provider directly in the same transaction.
- Keytag -> channel id. "Mimics": UTxOs with a matching IOU key and tag must be managed safely.

## Decision

### Overview

Subbit speaks two wire dialects, `vanilla` (its own native CBOR format) and `x402` (v2, the
`batch-settlement` scheme on Cardano). Both drive the same business logic
(`subbit_server::Ctx::handle_spend`/`handle_refund`); a dialect governs wire encoding/decoding
only. `subbit-l2-dto`'s crate-root types (`Request`, `Commit`, `Terms`, `Response`, `Status`, ...)
are dialect-agnostic; `vanilla` re-exports each as-is, `x402` wraps them in its own spec-shaped
envelopes (`dialect::x402::spec`) where its wire format needs more than a bare re-export.

The validator script hash is a provider-advertised parameter, not fixed: providers advertise
which script they use via `Terms`, consumers decide whether to accept it.

### x402 specifics

`batch-settlement`'s own spec (`specs/schemes/batch-settlement/scheme_batch_settlement.md`)
describes exactly Subbit's model under "Payment channel streaming," with "capital-backed" as a
named trust model; no Cardano network binding exists upstream, so this dialect is that binding,
not a rename of some other scheme.

- Headers, not a JSON body: `PAYMENT-SIGNATURE` (client -> server), `PAYMENT-REQUIRED`/
  `PAYMENT-RESPONSE` (server -> client), each base64 JSON.
- `PaymentPayload`/`PaymentRequirements`/`SettlementResponse` are x402's own generic vocabulary
  (`dialect::x402::spec`); `Require`/`Request`/`Response` are Subbit's own instantiations of them.
- `accepted` (the `PaymentRequirements` entry a client is paying under) is echoed back by the
  client and checked against what the provider currently offers for that URL; a stale or
  mismatched echo is a decode-time rejection.
- The scheme's required non-empty commitment identifier on success is the channel's own
  `Keytag`, stringified: available uniformly across every payload case, without inventing new
  crypto material.
- Subbit's own channel status/session `Mac` (`Status`) ride in `SettlementResponse.extensions`,
  concretely typed (`SettlementResponse<E>`, mirroring `PaymentPayload<A, P>`); `success`/`error`
  are hoisted onto the envelope's own fields rather than duplicated inside `extensions`.
- Network id is CAIP-2's human-readable form (`cardano:mainnet`/`preprod`/`preview`), per the
  scheme spec's own stated preference; CIP-34's numeric form is accepted as an input alias.
  Known gap: `accepted_matches` doesn't yet accept both forms for an echoed `accepted.network`
  (tracked in `TODO.md`).

### Facilitator

No first-class facilitator. This would be a role distinct from provider and consumer, where the
provider outsources chain-watching to a third party; it erodes the trustlessness guarantee
Subbit gives the provider, so it isn't prioritized. A provider can still outsource the whole
Subbit integration to a third party wholesale, outside the protocol.

## Consequences

- Two wire dialects to maintain and test: each needs its own adapter tests
  (`subbit-server`/`subbit-issuer`'s `dialect::{vanilla,x402}` modules), on top of the shared
  `Ctx` tests that cover business logic once.
- No facilitator means every provider does its own chain-watching, same as the rest of Subbit's
  design.
